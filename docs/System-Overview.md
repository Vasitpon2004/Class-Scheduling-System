## 1. ระบบนี้แก้ปัญหาอะไร

### ปัญหา

อาจารย์ที่ต้องนัดสอบหรือนัดเรียนชดเชยกับนิสิตกลุ่มใหญ่ ต้องหาช่วงเวลาที่ **ทุกคนว่างพร้อมกัน** ซึ่งทำด้วยมือแล้วยากขึ้นตามจำนวนคน

```
นิสิต 1 คน   → ถามครั้งเดียว
นิสิต 40 คน  → ต้องเทียบตารางเรียน 40 ชุด
             → แต่ละคนลงวิชาต่างกัน เวลาว่างจึงต่างกันหมด
```

วิธีที่ใช้กันทั่วไปคือถามในกลุ่มแชตแล้วรอคนตอบ ซึ่งมีปัญหา 3 ข้อ

| ปัญหา | ผลที่เกิด |
|---|---|
| คนตอบไม่ครบ | นัดไปแล้วค่อยรู้ว่ามีคนมาไม่ได้ |
| ไม่รู้ว่าใครยังไม่ตอบ | ต้องไล่ทวงทีละคน |
| เวลาที่เสนอชนกับคาบเรียน | ต้องเริ่มหาใหม่ทั้งรอบ |

### สิ่งที่ระบบทำ

ระบบรู้ตารางเรียนของนิสิตทุกคนอยู่แล้ว (จากการที่นิสิตเข้าห้องเรียนในระบบ) จึง **คำนวณเวลาว่างร่วมกันให้ก่อนที่อาจารย์จะเสนอนัด**

```
อาจารย์เลือกหมู่เรียน → ระบบดูว่าสมาชิกทุกคนในหมู่นั้นติดคาบเรียนช่วงไหน
                      → เสนอช่วงเวลาที่ว่างร่วมกัน
                      → อาจารย์เลือกแล้วสร้างนัด
                      → นิสิตตอบรับ/ปฏิเสธ พร้อมเหตุผล
                      → อาจารย์เห็นสรุปว่าใครตอบอะไร ใครยังไม่ตอบ
```

**จุดต่างจากเครื่องมือนัดหมายทั่วไป** (เช่น Google Calendar, When2meet) คือระบบไม่ต้องรอให้แต่ละคนมากรอกเวลาว่างของตัวเอง เพราะมันคำนวณจาก **ตารางเรียนจริง** ที่มีอยู่ในระบบแล้ว

## 2. ผู้ใช้งาน 3 บทบาท

| บทบาท | ค่าใน DB | ทำอะไรได้ |
|---|---|---|
| **นิสิต** | `'นิสิต'` | สมัคร · เข้าห้องเรียน · ดูนัดหมายของตัวเอง · ตอบรับ/ปฏิเสธนัด พร้อมเหตุผล |
| **อาจารย์** | `'อาจารย์'` | สมัคร (ต้องรอแอดมินอนุมัติ) · ดูสมาชิกในหมู่ที่สอน · **สร้างนัดหมาย** · ดูเวลาว่างร่วม · ดูสรุปคำตอบ · ยืนยัน/ยกเลิกนัด |
| **แอดมิน** | `'แอดมิน'` | อนุมัติ/ปฏิเสธคำขอเป็นอาจารย์ · จัดการรายวิชาและหมู่เรียน · นำนิสิตออกจากห้อง · รีเซ็ตภาคการเรียน · ดูบันทึกกิจกรรมของระบบ |

### ความต่างที่สำคัญระหว่างการสมัครของนิสิตกับอาจารย์

```
นิสิต   สมัคร → ยืนยันอีเมล → เข้าใช้งานได้ทันที
อาจารย์ สมัคร → ยืนยันอีเมล → รอแอดมินอนุมัติ → เข้าใช้งานได้
```

**เหตุผล** นิสิตมีอีเมล `@ku.th` ก็เพียงพอจะยืนยันว่าเป็นคนในมหาวิทยาลัย · แต่บทบาทอาจารย์ให้อำนาจสร้างนัดหมายและเห็นข้อมูลนิสิตทั้งหมู่ จึงต้องมีคนตรวจก่อนว่าเป็นอาจารย์จริง

ในฐานข้อมูลเก็บเป็นสองคอลัมน์แยกกัน และ `AuthService.login()` ตรวจทั้งคู่

| คอลัมน์ | ความหมาย | ใครตั้งค่า |
|---|---|---|
| `is_email_verified` | ยืนยันอีเมลแล้ว | ระบบ OTP |
| `is_approved` | ได้รับอนุมัติแล้ว | นิสิต = `TRUE` อัตโนมัติ · อาจารย์ = แอดมิน |

### ข้อมูลที่แต่ละบทบาทต้องกรอก

| บทบาท | ฟิลด์ที่บังคับ | รูปแบบ |
|---|---|---|
| นิสิต | ชื่อ · สกุล · อีเมล · รหัสผ่าน · **รหัสนิสิต · ชั้นปี · แผนการเรียน · สาขา** | ชั้นปี 1–8 · รหัสนิสิตเป็นตัวเลข |
| อาจารย์ | ชื่อ · สกุล · อีเมล · รหัสผ่าน · **รหัสประจำตัวบุคลากร** | `[A-Z]` 1 ตัว + เลข 4 หลัก เช่น `Q1234` |
| แอดมิน | สมัครผ่าน API ไม่ได้ | สร้างด้วย SQL |

**เหตุผลที่บังคับรหัสประจำตัวอาจารย์** — ขั้นตอนอนุมัติมีไว้เพื่อให้คนตรวจว่าเป็นอาจารย์จริง แต่ถ้าแอดมินเห็นแค่ชื่อกับอีเมล (ซึ่งใครก็กรอกได้) เขาก็ไม่มีอะไรไปเทียบ · รหัสประจำตัวบุคลากรทำให้แอดมินตรวจกับทะเบียนของคณะได้จริง — มันจึงไม่ใช่ข้อมูลประดับ แต่เป็นข้อมูลที่ทำให้ด่านอนุมัติทำงานได้

**และระบบแปลงรหัสเป็นตัวพิมพ์ใหญ่ก่อนบันทึกเสมอ** เพราะ `UNIQUE` ของ PostgreSQL เทียบตัวพิมพ์เล็กใหญ่ ถ้าไม่แปลง `Q1234` กับ `q1234` จะถือเป็นคนละค่า แล้วคนเดียวกันจะมีบัญชีซ้ำได้โดยที่ระบบไม่รู้

### บัญชีแอดมินคนแรกมาจากไหน

ระบบ **ปฏิเสธการสมัครด้วย `role: 'แอดมิน'`** โดยเจตนา (`POST /users` ตอบ 400) จึงเกิดปัญหา bootstrap คือ "ต้องมีแอดมินเพื่อสร้างแอดมิน"

ทางแก้มาตรฐานคือใส่คนแรกเข้าไป **นอกช่องทางปกติ** — `INSERT` ตรงในฐานข้อมูลพร้อม bcrypt hash ที่สร้างไว้ล่วงหน้า · จากนั้นแอดมินคนถัดไปสร้างผ่านระบบได้ (ยังไม่ได้ทำ เป็นงานลำดับถัดไป)

## 3. Tech Stack

### โครงสร้างโปรเจกต์

```
Class-Scheduling-System/
├── backend/          NestJS + TypeORM + PostgreSQL
├── frontend/         React + Vite + Tailwind CSS
├── docs/             เอกสารประกอบและ schema ของฐานข้อมูล
├── .gitignore
└── README.md         วิธีรันทั้งสองฝั่ง
```

**รวมไว้ repo เดียว แยกเป็นโฟลเดอร์** — สองฝั่งมี `package.json` และ `node_modules` ของตัวเอง ไม่ได้ปนกัน แต่ clone ครั้งเดียวได้ของครบ และ commit ที่แก้ทั้ง endpoint และหน้าจอที่เรียกมันเป็น commit เดียว ซึ่งทำให้ย้อนอ่านประวัติรู้เรื่อง

**ไม่ได้ใช้ monorepo tooling** (npm workspaces / Nx / Turborepo) เพราะไม่มี package ที่ใช้ร่วมกันระหว่างสองฝั่ง — สองฝั่งคุยกันผ่าน HTTP ไม่ใช่ผ่านการ import

### Frontend

| สิ่งที่ใช้ | บทบาท |
|---|---|
| **React** + **Vite** | UI และ build tool |
| **TypeScript** | ภาษา |
| **Tailwind CSS** | จัดรูปแบบหน้าเว็บ |

### Backend

| หมวด | สิ่งที่ใช้ | บทบาท |
|---|---|---|
| Runtime | **Node.js** (ES Module) | ตัวที่รันโค้ด · เป็นเหตุผลที่ import ต้องลงท้าย `.js` |
| ภาษา | **TypeScript** | |
| Framework | **NestJS 12** | โครง Module / Controller / Service / Guard / Pipe |
| ORM | **TypeORM** | ตั้ง `synchronize: false` — ฐานข้อมูลเป็นฝ่ายนำ entity เป็นฝ่ายตาม |
| Driver | `pg` | TypeORM โหลดตอน runtime |
| ตั้งค่า | `@nestjs/config` | อ่าน `.env` ผ่าน `ConfigService` |
| Validation | `class-validator` + `class-transformer` | `ValidationPipe` แบบ global |

| เอกสาร API | `@nestjs/swagger` | Swagger UI ที่ `/api` |
| สุ่มเลข | `node:crypto` | `randomInt` สำหรับ OTP — ไม่ใช้ `Math.random()` |

### หลักที่ใช้เลือกเครื่องมือ

**เลือกไลบรารีสำหรับงานด้านความปลอดภัย ไม่เขียนเอง** — bcrypt, Passport, JWT, throttler ล้วนเป็นโค้ดที่คนใช้เป็นล้านและถูกตรวจสอบแล้ว ปลอดภัยกว่าโค้ด 30 บรรทัดที่เขียนคนเดียวและไม่มีใครรีวิว

**เลือกตามเอกสารทางการเพื่อให้อ้างอิงได้** — หน้า docs ของ NestJS ที่ใช้จริงคือ `/first-steps`, `/application/validation`, `/data/typeorm`, `/recipes/passport`, `/guards`, `/custom-decorators`, `/security/rate-limiting`, `/openapi/introduction`

> **แต่ docs ให้แค่เครื่องมือ** — การออกแบบ schema 15 ตาราง, ลำดับด่านตรวจ OTP, ลำดับการเขียน log ก่อน DELETE, การตัดสินใจเรื่อง Transaction, นโยบาย status code เป็นส่วนที่ออกแบบเอง และเป็นส่วนที่เป็นผลงานจริงของโครงงาน

## 4. สถาปัตยกรรมภาพรวม

```
┌─────────────────────────────────────────┐
│  Frontend — React + Vite + Tailwind     │
│  หน้าเว็บ · เก็บ token · ซ่อนเมนูตาม role  │
└──────────────────┬──────────────────────┘
                   │  HTTP + JSON
                   │  Authorization: Bearer <JWT>
┌──────────────────▼──────────────────────┐
│  Backend — NestJS                        │
│                                          │
│  ① ThrottlerGuard   นับจำนวนครั้งต่อ IP    │
│  ② Guard            ตรวจ token + สิทธิ์    │
│  ③ Pipe             ตรวจรูปแบบข้อมูล       │
│  ④ Controller       รับ HTTP              │
│  ⑤ Service          business logic        │
│  ⑥ Repository       TypeORM → SQL         │
└──────────────────┬──────────────────────┘
                   │  SQL
┌──────────────────▼──────────────────────┐
│  PostgreSQL 16                           │
│  CHECK · UNIQUE · FK — ด่านสุดท้าย         │
└─────────────────────────────────────────┘
```

**ลำดับชั้นนี้เรียงตามราคาของงาน** — ปฏิเสธด้วยการนับเลข (ถูกที่สุด) ก่อนตรวจ token ก่อนตรวจรูปแบบข้อมูล ก่อนแตะฐานข้อมูล (แพงที่สุด)

### การแบ่งความรับผิดชอบระหว่าง 3 ชั้น

| คำถาม | ใครตอบ |
|---|---|
| หน้าเว็บควรแสดงอะไร | Frontend |
| คนนี้เข้าได้ไหม มีสิทธิ์ไหม | Backend (Guard) |
| ข้อมูลที่ส่งมาถูกรูปแบบไหม | Backend (Pipe + DTO) |
| กฎทางธุรกิจผ่านไหม | Backend (Service) |
| ข้อมูลถูกต้องตามโครงสร้างไหม | PostgreSQL (constraint) |

**หลักที่ยึดตลอดโครงงาน**

> **ความถูกต้องของข้อมูลให้ฐานข้อมูลบังคับ · ความชัดเจนของข้อผิดพลาดให้ backend จัดการ**

ตัวอย่าง: ส่ง `role: "อาจารย์"` พร้อม `year: 3` — ฐานข้อมูลมี `chk_nisit_fields` ปฏิเสธอยู่แล้ว แต่ผู้ใช้จะได้ `500 Internal server error` ที่อ่านไม่รู้เรื่อง · การเช็กซ้ำที่ Service ทำให้ได้ `400 เฉพาะนิสิตเท่านั้นที่ระบุชั้นปีและแผนการเรียนได้` แทน

เรื่องเดียวกันใช้กับรหัสอาจารย์ — `chk_professor_code_format` ใน DB กันข้อมูลผิดรูปแบบไม่ให้เข้าตาราง แต่ถ้าปล่อยให้ DB ปฏิเสธจะได้ 500 · การเช็ก regex ที่ Service ทำให้ได้ 400 พร้อมบอกรูปแบบที่ถูกต้อง

**และ frontend validation ไม่นับเป็นด่าน** เพราะ HTTP request ปลอมได้ด้วย Swagger, Postman หรือ curl โดยไม่ผ่านหน้าเว็บเลย

```
หน้าเว็บ ──┐
          ├──→ POST /users   ← backend แยกไม่ออกว่ามาจากไหน
curl ─────┘
```

> **frontend validation มีไว้เพื่อประสบการณ์ที่ดี · backend validation มีไว้เพื่อความถูกต้อง**

### หลักที่ใช้ตัดสินว่าต้องใส่ด่านตรวจหรือไม่

เทียบต้นทุนสองฝั่ง

| ต้นทุนของการใส่ด่าน | ต้นทุนของการไม่ใส่ |
|---|---|
| โค้ด 3 บรรทัด · ไม่ต้องยิง DB เพิ่ม | ข้อมูลผิดเข้าตาราง หรือ log ที่บันทึกเรื่องที่ไม่เคยเกิด |
| ไม่กระทบความเร็ว | แก้ย้อนหลังไม่ได้ |

เมื่อสองฝั่งไม่สมมาตรแบบนี้ **ใส่ด่านไว้เสมอ แม้จะคิดว่าไม่มีทางเกิด** — ไม่ใช่เพราะทำนายว่าจะมีคนทำผิด แต่เพราะ service ไม่มีทางรู้ว่าใครเรียกมันและทำไม (หน้าเว็บ · Swagger · script · ปุ่มใหม่ในอนาคต) จึงต้องเขียนให้ถูกต้องเองโดยไม่พึ่งผู้เรียก

### โมดูลใน Backend และความสัมพันธ์

```
AppModule
 ├── ConfigModule        อ่าน .env
 ├── TypeOrmModule       ต่อ PostgreSQL
 ├── ThrottlerModule     + APP_GUARD (global)
 ├── FacultiesModule     คณะ + สาขา (ข้อมูลตั้งต้น)
 ├── UsersModule ─────┐
 ├── AuthModule ──────┤
 ├── OtpModule ◄──────┘  ทั้ง Users และ Auth ยืมใช้
 └── SystemLogsModule ◄── UsersModule ยืมใช้
```

**ลูกศรชี้ทางเดียวเสมอ**

```
SystemLogsModule  ←── UsersModule  ←── AuthModule
OtpModule         ←── UsersModule  ←── AuthModule
                  ←─────────────────────┘
```

**เหตุผลที่ OTP ต้องเป็นโมดูลแยก** เพราะทั้ง `UsersService` (ตอนสมัคร) และ `AuthService` (ตอนยืนยัน) ต้องใช้ · ถ้าเอาไปไว้ใน `AuthModule` จะเกิดวงกลมเพราะ `AuthModule` import `UsersModule` อยู่แล้ว

**`OtpModule` และ `SystemLogsModule` ไม่มี controller** — เป็นโมดูลที่ให้บริการโมดูลอื่น ไม่รับ HTTP เอง · endpoint ที่เกี่ยวข้องอยู่ใน `AuthController` และ `UsersController`

> **สัญญาณที่ใช้จับว่าวางหน้าที่ผิดที่** เวลาออกแบบแล้วรู้สึกว่า "โมดูลนี้ต้องดึงของจากที่อื่นมาเพิ่มเรื่อย ๆ" ให้สงสัยก่อนว่าหน้าที่นั้นอาจไม่ใช่ของโมดูลนั้น

### แกนกลางของการออกแบบ — รายวิชา 3 ชั้น

ส่วนที่ลึกที่สุดของ schema และเป็นส่วนที่ทำให้ระบบทำงานได้

```
courses                01418471  Software Design        ← ชื่อวิชาเก็บครั้งเดียว
    │
    ├── course_sections      หมู่ 700 เทอม 1/2569
    │        └── course_schedules   จันทร์ 13:00–16:00 ห้อง SC7-306
    │
    └── course_sections      หมู่ 800 เทอม 1/2569
             └── course_schedules   พฤหัสบดี 13:00–16:00 ห้อง SC7-306
```

**สองเรื่องที่ทำให้การวิเคราะห์เวลาว่างทำงานถูกต้อง**

**① ชื่อวิชาเก็บที่ `courses` ที่เดียว** ไม่ว่าจะเปิดกี่หมู่กี่เทอม · วิชาศึกษาทั่วไปบางตัวเปิด 16 หมู่ ถ้าเก็บชื่อซ้ำทุกหมู่แล้วมหาวิทยาลัยแก้ชื่อ จะมีทั้งชื่อเก่าและใหม่อยู่ในระบบพร้อมกัน

**② สมาชิกผูกกับ "หมู่เรียน" ไม่ใช่ "วิชา"**

```
ผิด   users → course_members → courses → ไม่มีเวลาเรียน
ถูก   users → course_members → course_sections → course_schedules → ได้เวลาเรียน
```

ถ้าสมาชิกชี้ไปที่ `courses` ระบบจะรู้แค่ว่า "เรียนวิชานี้" แต่ไม่รู้ว่าหมู่ไหน จึงไม่รู้เวลาเรียน แล้ว **การวิเคราะห์เวลาว่างร่วมกันซึ่งเป็นหัวใจของโครงงานจะทำไม่ได้เลย**

### ตารางที่ตัดทิ้งระหว่างการออกแบบ

| ตารางที่คิดไว้ตอนแรก | เหตุผลที่ตัด |
|---|---|
| `time_busy` (เก็บเวลาที่นิสิตติดเรียน) | หาได้จาก JOIN `course_members` → `course_sections` → `course_schedules` ทั้งหมด · ถ้าเก็บซ้ำ แล้วแอดมินแก้เวลาเรียน ข้อมูลจะไม่ตรงกันโดยไม่มีใครรู้ |
| `classrooms` (ตัวกลางระหว่างวิชากับสมาชิก) | ไม่ได้เพิ่มข้อมูลอะไร เพราะสมาชิกผูกกับหมู่เรียน ไม่ได้ผูกกับห้อง |

**ประวัติการแก้โครงสร้างมี 4 รุ่น** ทุกรุ่นดูถูกต้องตอนออกแบบ แต่พังเมื่อเอาข้อมูลจริงมาใส่ — เช่นวิชา `01355111` ที่เรียนทั้งจันทร์และพุธ ซึ่งโครงสร้างรุ่น 2 เก็บไม่ได้เลย · รายละเอียดอยู่ใน `Normalization.md` หัวข้อ 8

### CHECK constraint ของตาราง `users` — 5 ตัวที่ทำงานเป็นชุด

| Constraint | บังคับอะไร |
|---|---|
| `chk_ku_email` | อีเมลต้องลงท้าย `@ku.th` |
| `chk_nisit_fields` | คนที่ไม่ใช่นิสิต **ห้ามมี** `year`, `study_plan` |
| `chk_nisit_required` | นิสิต **ต้องมี** `year`, `study_plan`, `user_code`, `major_id` ครบ |
| `chk_professor_required` | อาจารย์ **ต้องมี** `user_code` |
| `chk_professor_code_format` | รหัสอาจารย์ต้องตรงรูปแบบ `^[A-Z][0-9]{4}$` |

**สองตัวสุดท้ายต้องมีคู่กัน ขาดตัวใดตัวหนึ่งไม่ได้** — เพราะถ้า `user_code` เป็น `NULL` นิพจน์ `NULL ~ '^[A-Z][0-9]{4}$'` จะได้ผลเป็น `NULL` ไม่ใช่ `false` และ **CHECK ที่ได้ผล `NULL` ถือว่าผ่าน** · ตัวหนึ่งกันค่าว่าง อีกตัวกันรูปแบบผิด

## 6. เส้นทางการใช้งานทั้งระบบ

### เส้นทางที่ 1 — สมัครและเข้าใช้งาน

```
กรอกฟอร์มสมัคร
   ↓ POST /users
ตรวจ: ไม่ให้สมัครเป็นแอดมิน · คนที่ไม่ใช่นิสิตห้ามส่งชั้นปี
      · รหัสอาจารย์ต้องตรงรูปแบบ (แปลงเป็นตัวพิมพ์ใหญ่ก่อน)
      · สาขามีจริง · อีเมลไม่ซ้ำ
   ↓ hash รหัสผ่านด้วย bcrypt
บันทึกบัญชี (นิสิตได้ is_approved = TRUE ทันที · อาจารย์ยังเป็น FALSE)
   ↓ สร้าง OTP 6 หลัก อายุ 10 นาที
   ↓ (ตอนนี้แสดงใน terminal · อนาคตส่งอีเมล)
กรอกรหัส OTP
   ↓ POST /auth/verify-otp
ตรวจ 4 ด่าน: ไม่พบรหัส · หมดอายุ · กรอกผิดเกิน 5 ครั้ง · รหัสไม่ตรง
   ↓ ผ่าน → is_email_verified = TRUE
เข้าสู่ระบบ
   ↓ POST /auth/login
ตรวจ: รหัสผ่าน · ยืนยันอีเมลแล้ว · ได้รับอนุมัติแล้ว · บัญชีไม่ถูกระงับ
   ↓
ได้ JWT อายุ 24 ชั่วโมง
```

**ขอรหัส OTP ใหม่ได้** ที่ `POST /auth/resend-otp` ซึ่งปิดรหัสเก่าทิ้งก่อนออกรหัสใหม่ เพื่อไม่ให้มีรหัสใช้ได้หลายตัวพร้อมกัน

### เส้นทางที่ 2 — อาจารย์รอการอนุมัติ ✅ ใช้งานได้จริงแล้ว

```
อาจารย์สมัคร + ยืนยันอีเมลแล้ว  →  is_approved ยังเป็น FALSE  →  login ได้ 403
                                            ↓
                              แอดมินเห็นรายการที่รออนุมัติ
                                            ↓
                ┌───────────────────────────┴───────────────────────────┐
         POST /users/:id/approve                            POST /users/:id/reject
                                                            body: { reason }
         ① หา user → ไม่เจอ 404                              ① หา user → ไม่เจอ 404
         ② role ต้องเป็นอาจารย์ → 400                          ② role ต้องเป็นอาจารย์ → 400
         ③ is_approved ต้องยัง false → 400                    ③ is_approved ต้องยัง false → 400
         ④ บันทึก log (target_user_id = id จริง)              ④ บันทึก log (target_user_id = NULL)
         ⑤ UPDATE is_approved = TRUE                         ⑤ DELETE บัญชี
                                            ↓
                                    อาจารย์ login ได้
```

**เหตุผลที่ปฏิเสธแล้วลบบัญชี** เพื่อให้คนที่ถูกปฏิเสธเพราะกรอกข้อมูลผิดสมัครใหม่ด้วยอีเมลเดิมได้ · ถ้าเก็บบัญชีไว้แล้วตั้ง `is_active = FALSE` เขาจะติด `UNIQUE` ของอีเมลและสมัครใหม่ไม่ได้ตลอดไป

**เหตุผลที่ log ของการปฏิเสธตั้ง `target_user_id = NULL`** เพราะบัญชีถูกลบไปแล้ว ถ้าใส่ `id` จริงจะลบไม่ได้ (FK เป็น `NO ACTION`) · ข้อมูลที่ต้องเก็บไว้จึงอยู่ใน `detail` เป็นข้อความ — อีเมล ชื่อ และเหตุผล

**เหตุผลที่ลำดับต้องเป็น log ก่อนแล้วค่อยเขียนทับ/ลบ** — ถ้าครึ่งหลังพัง เราได้สถานะที่กู้คืนได้ (มี log แต่ยังไม่ได้ทำ แอดมินกดซ้ำได้) แต่ถ้าสลับลำดับแล้วพัง เราจะเสีย log ไปถาวร

> **หลักเดียวกับที่ใช้ใน `OtpService.verify()`** — ให้สิ่งที่กู้คืนไม่ได้เกิดขึ้นก่อน

### เส้นทางที่ 3 — เตรียมห้องเรียน

```
แอดมินสร้างรายวิชา          courses
   ↓
แอดมินเปิดหมู่เรียนในภาคนี้   course_sections
   ↓
แอดมินใส่คาบเรียน            course_schedules  (1 หมู่มีได้หลายคาบ)
   ↓
แอดมินกำหนดอาจารย์ผู้สอน     course_professors
   ↓
นิสิตเข้าห้องเรียน            course_members
```

**ขั้นที่นิสิตเข้าห้องเรียนคือขั้นที่ป้อนข้อมูลให้ระบบวิเคราะห์ได้** — เมื่อนิสิตอยู่ในหมู่เรียน ระบบก็รู้ว่าเขาติดคาบเรียนช่วงไหนโดยอัตโนมัติ ไม่ต้องให้เขามากรอกเวลาว่างเอง

### เส้นทางที่ 4 — นัดหมาย (เส้นทางหลักของโครงงาน)

```
อาจารย์เลือกหมู่เรียนที่จะนัด
   ↓
ระบบวิเคราะห์เวลาว่างร่วมกันของสมาชิกทุกคนในหมู่
   ↓
อาจารย์เลือกช่วงเวลา + กรอกหัวข้อ ประเภท (นัดสอบ / นัดเรียนชดเชย)
   ห้อง อาคาร และกำหนดเวลาที่ต้องตอบ (response_deadline)
   ↓
ระบบสร้างนัด + สร้างแถวคำตอบให้สมาชิกทุกคนพร้อมกัน  ← ต้องใช้ Transaction
   status = 'รอ' ทุกแถว
   ↓
นิสิตเห็นนัดหมาย → ตอบรับ หรือ ปฏิเสธพร้อมเหตุผล
   (CHECK บังคับว่าถ้าปฏิเสธต้องมีเหตุผล)
   ↓
อาจารย์เห็นสรุป: ตอบรับกี่คน ปฏิเสธกี่คน ยังไม่ตอบกี่คน + เหตุผลของคนที่ปฏิเสธ
   ↓
อาจารย์ยืนยันนัด หรือ ยกเลิกแล้วหาเวลาใหม่
```

**ทำไมขั้นสร้างนัดต้องใช้ Transaction** เพราะ "สร้างนัด" กับ "สร้างแถวคำตอบของสมาชิกทุกคน" เป็นสองการเขียนที่ **ไร้ความหมายถ้าขาดอีกอย่าง** — มีนัดแต่ไม่มีใครได้รับแจ้ง นัดนั้นก็ไม่มีประโยชน์

นี่เป็นจุดเดียวในระบบที่เข้าเกณฑ์ Transaction จริง · จุดอื่นที่เขียน DB สองครั้ง (สมัคร+OTP, ยืนยัน+อัปเดตสถานะ, อนุมัติ+log, ปฏิเสธ+ลบบัญชี) เลือกไม่ใช้ Transaction เพราะความเสียหายกู้คืนได้

### เส้นทางที่ 5 — ปลายภาคการศึกษา

```
แอดมินสำรองข้อมูลภาคเรียน    semester_backups  (ต้องสำเร็จก่อน)
   ↓  CHECK บังคับว่าถ้า status = 'สำเร็จ' ต้องมี file_path
แอดมินรีเซ็ตภาคการเรียน
   ↓
เปิดภาคใหม่  (partial unique index บังคับว่ามีภาคที่ is_active = TRUE ได้ทีละภาคเดียว)
```

## 7. หัวใจของระบบ — การวิเคราะห์เวลาว่างร่วมกัน

ส่วนนี้คือสิ่งที่ทำให้โครงงานนี้ต่างจากระบบนัดหมายทั่วไป และเป็นส่วนที่ยังไม่ได้ลงมือเขียน

### แนวคิด

ระบบไม่ถามนิสิตว่าว่างเมื่อไหร่ แต่ **อนุมานจากตารางเรียน**

```
เวลาว่างของนิสิตคนหนึ่ง = ช่วงเวลาทั้งหมดในสัปดาห์ − ช่วงที่ติดคาบเรียน − ช่วงที่ติดนัดหมายอื่น
เวลาว่างร่วมของหมู่เรียน = ช่วงที่ไม่มีสมาชิกคนไหนติดอะไรเลย
```

### การตรวจมี 2 ชั้น

| ชั้น | ตรวจอะไร | Query ที่ร่างไว้ | ข้ามได้ไหม |
|---|---|---|---|
| ชั้นที่ 1 | หานิสิตที่ติด**คาบเรียนปกติ** | `Query 4` | **ข้ามได้** ถ้าวันที่เลือกอยู่ในช่วงสอบ (เพราะช่วงสอบไม่มีการเรียนปกติ) |
| ชั้นที่ 2 | หานิสิตที่ติด**นัดหมายของอาจารย์คนอื่น** | `Query 5` | **ข้ามไม่ได้ไม่ว่ากรณีใด** |

การตรวจว่าวันที่เลือกอยู่ในช่วงสอบหรือไม่คือ `Query 2` ซึ่งอ่านจาก `semesters.midterm_start_date` / `final_start_date`

### ข้อมูลที่ต้องเดินผ่าน 4 ชั้น

```
course_members      ใครอยู่หมู่ไหน
      ↓
course_sections     หมู่นั้นคือวิชาอะไร เทอมอะไร
      ↓
course_schedules    หมู่นั้นเรียนวันไหน เวลาไหน
      ↓
เทียบทุกคนในหมู่ที่ต้องการนัด  →  หาช่วงที่ไม่ชนกับใครเลย
```

**สิ่งที่ต้องระวังในการคำนวณ** — นิสิตคนหนึ่งอยู่หลายหมู่เรียน (ลงหลายวิชา) ดังนั้นเวลาที่เขาติดคือเวลาของ **ทุกหมู่ที่เขาเป็นสมาชิก** รวมกัน ไม่ใช่แค่หมู่ที่กำลังจะนัด

### Index ที่รองรับเส้นทางนี้

JOIN 4 ชั้นจะช้าถ้าไม่มี index · หลายตัวไม่ต้องประกาศเพิ่มเพราะ `UNIQUE` สร้างให้แล้วตามกฎ Leftmost Prefix

| เส้นทางที่ใช้บ่อย | Index ที่ใช้ | มาจาก |
|---|---|---|
| หาสมาชิกของหมู่ | `uq_section_member (section_id, user_id)` | UNIQUE constraint |
| หาหมู่ที่นิสิตเรียน | `idx_members_user (user_id)` | ประกาศเพิ่ม |
| หาคาบเรียนของหมู่ | `uq_course_schedule (section_id, course_day, start_time)` | UNIQUE constraint |
| ตรวจนัดหมายซ้อน | `idx_appointment_conflict (appointment_date, status)` | ประกาศเพิ่ม |

### สถานะ

ยังไม่ได้เขียน · เป็นลำดับที่ 5 ในแผนงาน และต้องผ่าน entity 3 ชั้นของรายวิชา + สมาชิกห้องเรียน + นัดหมายก่อน

Query ที่ร่างไว้อยู่ในไฟล์ `docs/queries.sql` (Query 4 และ 5) · ตอนลงมือต้องตัดสินใจว่าจะเขียนด้วย QueryBuilder ของ TypeORM หรือ Raw SQL ซึ่งน่าจะเป็น Raw SQL เพราะเป็น query ที่ซับซ้อนเกินกว่าที่ QueryBuilder จะอ่านง่าย

## 8. ความปลอดภัยของระบบ

### มาตรการที่ทำแล้ว

| ชั้น | มาตรการ | ป้องกันอะไร |
|---|---|---|
| รหัสผ่าน | **bcrypt** cost 10 · salt ฝังในสตริง hash | ถ้า DB รั่ว รหัสผ่านไม่หลุด · กัน rainbow table |
| | `password_hash` ตั้ง `select: false` | hash ไม่ติดมาใน response โดยไม่ได้ตั้งใจ |
| Token | **JWT** อายุ 24 ชม. · ใส่แค่ `sub` และ `role` | ไม่มีความลับอยู่ใน payload ที่ใครก็ถอดอ่านได้ |
| ตัวตน | **JwtAuthGuard** (Passport) ตรวจลายเซ็น + วันหมดอายุ | 401 เมื่อไม่รู้ว่าเป็นใคร |
| สิทธิ์ | **RolesGuard** + `@Roles([...])` | 403 เมื่อรู้ว่าเป็นใครแต่ไม่มีสิทธิ์ |
| ข้อมูลขาเข้า | **ValidationPipe** `whitelist` + `forbidNonWhitelisted` | **mass assignment** — กันคนส่ง `is_approved: true` มาเอง |
| | ปฏิเสธ `role: 'แอดมิน'` ที่ Service | กันการสมัครเป็นแอดมิน |
| | ตรวจ `role` และ `is_approved` ก่อนอนุมัติ/ปฏิเสธ | กันการอนุมัติคนผิด และกัน **log ที่บันทึกเรื่องที่ไม่เคยเกิด** |
| SQL | **parameterized query** (`:email`) | **SQL Injection** |
| ความถี่ | **Throttler** login 5/นาที · resend-otp 1/นาที | การเดารหัสผ่านซ้ำ ๆ และการกวนอีเมล |
| ข้อความ error | 401 ข้อความเดียวกันทั้งกรณี "ไม่พบอีเมล" และ "รหัสผิด" | **user enumeration** |
| OTP | อายุ 10 นาที · ใช้ครั้งเดียว · ผิดได้ 5 ครั้ง · ปิดรหัสเก่าเมื่อออกใหม่ | การเดารหัส 6 หลักและการใช้รหัสเก่าซ้ำ |
| ความลับ | `.env` + `.gitignore` · `getOrThrow` สำหรับ `JWT_SECRET` | secret หลุดขึ้น GitHub · และพังตอน start ถ้าลืมตั้งค่า แทนที่จะพังเงียบ ๆ |
| การตรวจสอบย้อนหลัง | `system_logs` บันทึกว่าใครทำอะไรกับใครเมื่อไหร่ · `detail` เป็น snapshot | ไม่มีใครเปลี่ยนสถานะคนอื่นได้โดยไม่มีร่องรอย |
| ฐานข้อมูล | CHECK 12 ตัว · UNIQUE · FK เป็นด่านสุดท้าย | ข้อมูลเสียหายแม้โค้ดมีบั๊ก |

### เรื่องที่ต้องอธิบายได้ว่าทำไมเลือกแบบนี้

**401 กับ 403 ต่างกันและมีผลกับ frontend** — 401 แปลว่า "ไม่รู้ว่าคุณเป็นใคร" หน้าบ้านควรเด้งไป login · 403 แปลว่า "รู้ว่าคุณเป็นใคร แต่ทำไม่ได้" ควรแสดงข้อความเฉย ๆ ไม่ต้องเด้ง · ถ้าส่ง 401 ตอน "รออนุมัติ" ผู้ใช้จะถูกเด้งวนโดยไม่เห็นเหตุผล

**การซ่อนเมนูตาม role ไม่ใช่ความปลอดภัย** — หน้าเว็บซ่อนเมนู "จัดการผู้ใช้" จากนิสิตได้ แต่นิสิตยิง `GET /users` ตรงได้อยู่ดี · `RolesGuard` คือด่านจริง

**`GET /auth/me` ปลอดภัยกว่า `GET /users/:id`** — แบบที่มีเลขใน URL ผู้ใช้เปลี่ยนเลขเพื่อดูข้อมูลคนอื่นได้ แล้วต้องเขียนโค้ดเช็กเพิ่ม · แบบ `/me` ไม่มีเลขให้แก้ตั้งแต่แรก

> **ช่องโหว่ที่ออกแบบให้ไม่มีอยู่ ดีกว่าช่องโหว่ที่ต้องจำไว้ปิด**

**log ต้องไม่กลืน error** — `SystemLogsService.record()` ไม่มี `try/catch` โดยเจตนา ถ้าบันทึกไม่สำเร็จต้องให้ทั้งรายการล้มเหลว ไม่ใช่เดินต่อไปลบบัญชี · ตรงข้ามกับ OTP ที่กลืน error ได้เพราะขอรหัสใหม่ได้

> **การกลืน error ไม่ดีหรือแย่ในตัวเอง — มันขึ้นกับว่าสิ่งที่ล้มเหลวนั้นกู้คืนได้หรือไม่**

### เหตุการณ์ด้านความปลอดภัยที่เกิดขึ้นจริงและแก้แล้ว

**8 ต.ค. 2569** พบว่า `backend/.env` ถูก git ติดตามไว้ตั้งแต่ commit แรก เพราะไฟล์ `.gitignore` พิมพ์ชื่อผิดเป็น `.gitinore` จึงไม่เคยมีผล และ repo เป็น public

**สิ่งที่ทำ** — ปิด repo เป็น private ชั่วคราว → เปลี่ยน `JWT_SECRET` เป็นค่าสุ่ม 48 ไบต์ → เปลี่ยนรหัสบัญชีแอดมิน → `git rm --cached` เลิกติดตาม `.env` / `node_modules` / `dist` → แก้ชื่อไฟล์ `.gitignore` → ยืนยันบน GitHub ว่าไฟล์หายจริง

**บทเรียนที่ได้ และควรตอบได้ถ้าถูกถาม**

```
.gitignore ห้ามของใหม่เข้า แต่ไม่ขับของเก่าออก
   ไฟล์ที่ git เคยรับเข้า repo แล้วจะถูกติดตามต่อไปโดยไม่สนใจ .gitignore
   ต้องใช้ git rm --cached เท่านั้น
```

**และเลือกไม่ลบออกจาก git history** เพราะการเขียนประวัติทั้ง repo ใหม่ไม่ได้ช่วยอะไรเพิ่ม — สิ่งที่ทำให้ค่าที่หลุดไร้ประโยชน์คือการเปลี่ยนค่า ไม่ใช่การลบร่องรอย

## 9. สถานะปัจจุบัน

```
▓▓▓▓▓▓▓▓▓▓░░░░░░░░░░   ประมาณ 50% ของงาน backend
```

> ตัวเลขนี้เป็น**การประมาณ** จากจำนวนฟีเจอร์ที่เสร็จเทียบกับที่วางแผนไว้ ไม่ได้มาจากการวัดบรรทัดโค้ดหรือชั่วโมงทำงาน

### ✅ เสร็จแล้ว

| ส่วน | รายละเอียด |
|---|---|
| ฐานข้อมูล | 15 ตาราง · 3NF ผ่าน BCNF · CHECK 12 ตัว · รันจริงแล้ว |
| โครงโปรเจกต์ | NestJS + TypeORM + ValidationPipe + Swagger · repo รวม frontend/backend/docs |
| คณะ / สาขา | `GET /faculties`, `GET /faculties/:id` |
| สมัครสมาชิก | `POST /users` + ปิดช่องโหว่ 5 จุด + บังคับรหัสประจำตัวตามบทบาท |
| เข้าสู่ระบบ | `POST /auth/login` + JWT (Passport) |
| สิทธิ์ตามบทบาท | `JwtAuthGuard` + `RolesGuard` + `@Roles` |
| ยืนยันอีเมล | OTP ครบทั้งเส้น — สร้าง · ยืนยัน · ขอใหม่ (ยังไม่ส่งอีเมลจริง) |
| จำกัดความถี่ | Throttler ทั้งแบบ global และเฉพาะจุด |
| โปรไฟล์ | `GET /auth/me` + `@CurrentUser()` |
| บันทึกกิจกรรม | entity + service + ใช้งานจริงแล้วใน 2 endpoint |
| **อนุมัติ / ปฏิเสธอาจารย์** | `POST /users/:id/approve` · `POST /users/:id/reject` — **เส้นทางของอาจารย์เดินได้ครบวงแล้ว** |

### ⬜ ยังไม่เริ่ม

```
สร้างแอดมินผ่าน API  →  รายวิชา 3 ชั้น  →  เข้าห้องเรียน  →  สร้างนัดหมาย
                                                  →  วิเคราะห์เวลาว่าง ★  →  สรุปผลตอบกลับ
```

บวกงานที่ตัดได้ถ้าเวลาไม่พอ — ส่งอีเมลจริง · หน้าดู log · แจ้งเตือน Discord · รีเซ็ตภาคเรียน

### เส้นทางที่เดินได้จริงแล้วตอนนี้

```
นิสิต    สมัคร → OTP → ยืนยัน → login ได้
อาจารย์  สมัคร (ต้องมีรหัส Q1234) → OTP → ยืนยัน → login ได้ 403 "รออนุมัติ"
                                            ↓
                          แอดมินกด approve → อาจารย์ login ได้
                          แอดมินกด reject  → บัญชีถูกลบ + log เก็บเหตุผลไว้
   ↑                                              ↓
ขอรหัสใหม่ได้          GET /auth/me (ทุกคน) · GET /users (แอดมิน) · system_logs (ดูใน pgAdmin)
```

### การทดสอบ

ทดสอบผ่าน Swagger UI ทุก endpoint

| ฟีเจอร์ | จำนวนเคส | ผล |
|---|---|---|
| Guard + Roles | 4 | ผ่าน (401 / 403 / 403 / 200) |
| OTP ทั้งเส้น | 11 | ผ่าน |
| `GET /auth/me` | 4 | ผ่าน |
| Rate limiting | — | ผ่าน (429 ตามเพดาน และกลับมาใช้ได้หลังครบนาที) |
| อนุมัติ / ปฏิเสธอาจารย์ | 5 | ผ่าน |
| รูปแบบรหัสอาจารย์ | 3 | ผ่าน |

**ยังไม่มี automated test** — เป็นงานที่ควรทำถ้าเวลาเหลือ และควรระบุไว้ในข้อจำกัดของเล่ม

## 10. ข้อจำกัดที่รู้แล้ว

เขียนไว้เพื่อตอบอาจารย์ได้ตรงไปตรงมา — **รู้และเลือกแลก ไม่ใช่นึกไม่ถึง**

| เรื่อง | คำอธิบาย |
|---|---|
| รูปแบบรหัสอาจารย์ `[A-Z]\d{4}` เป็นสมมติฐาน | ยังไม่ได้ตรวจกับทะเบียนของคณะ · ถ้ารูปแบบจริงต่างจากนี้ อาจารย์บางคนจะสมัครไม่ได้ · แก้ได้ใน 2 นาที (DROP แล้ว ADD CONSTRAINT ใหม่ + แก้ regex ใน service ให้ตรงกัน) |
| รูปแบบรหัสนิสิตยังไม่ได้บังคับ | ตรวจแค่ว่ามีค่า ไม่ตรวจว่าเป็นเลข 10 หลัก · ไม่สมมาตรกับอาจารย์ |
| คนที่ถูกปฏิเสธไม่ได้รับแจ้ง | `reason` เก็บไว้ใน `system_logs.detail` ซึ่งมีแต่แอดมินเห็น · รอต่อ Nodemailer |
| ยังไม่มี endpoint ดูรายชื่อที่รออนุมัติ | `GET /users` คืนทุกคน ยังกรองไม่ได้ · หน้าบ้านกรองเองได้ชั่วคราว |
| OTP ยังไม่ส่งอีเมลจริง | กลไกยืนยันอีเมลทำครบแล้ว เหลือแต่ช่องทางส่ง ซึ่งเป็นการเปลี่ยนโค้ดบรรทัดเดียว |
| OTP เก็บเป็นข้อความธรรมดา | ยอมรับได้เพราะอายุ 10 นาที ใช้ครั้งเดียว ผิดได้ 5 ครั้ง · ต่างจากรหัสผ่านที่อยู่ถาวร |
| rate limit เก็บตัวนับในหน่วยความจำ | รีสตาร์ทแล้วรีเซ็ต · รันหลาย instance แล้วนับแยกกัน · ระบบใหญ่ใช้ Redis |
| rate limit นับตาม IP ไม่ใช่ตามอีเมล | คนร้ายที่มีหลาย IP ยังกวนอีเมลเหยื่อได้ |
| user enumeration ยังไม่ปิดสนิท | `POST /users` ตอบ 409 ซึ่งบอกว่าอีเมลมีอยู่ · การปิดที่ endpoint อื่นเป็นการไม่เพิ่มช่องใหม่ ไม่ใช่การอุดช่องที่มี |
| Race condition ตอนเช็คอีเมลซ้ำ | ฐานข้อมูลกันข้อมูลเสียแล้ว เสียแค่ status code (500 แทน 409) |
| การเขียน DB สองครั้งไม่มี Transaction ครอบ | 4 จุด · เลือกลำดับที่ความเสียหายกู้คืนได้ และพึ่ง `resend-otp` / การกดซ้ำ เป็นทางออก |
| Token ยกเลิกก่อนหมดอายุไม่ได้ | JWT ไม่เก็บรายการที่ server · จำกัดความเสียหายด้วยอายุ 24 ชม. |
| `role` ใน token ค้างเป็นค่าเก่า | ถ้าแอดมินเปลี่ยน role ของใคร token เดิมยังใช้สิทธิ์เก่าได้จนหมดอายุ |
